# 踩坑记录

> 本项目开发过程中实际踩过的坑，按「现象 → 根因 → 解决 → 教训」记录。
> 改代码前扫一眼，能省很多时间。新增踩坑请往后面追加。

---

## 1. 采样率和位深互相覆盖

- **现象**：选 192kHz 输出，位深被压回 16-bit；选 24-bit，采样率被打回 44.1k。
- **根因**：WAV 输出 codec 硬编码 `pcm_s16le`，与 `-sample_fmt flt` 冲突——FFmpeg 里 codec 和 sample_fmt 会互相覆盖。
- **解决**：按目标位深动态选 codec，完全不用 `-sample_fmt`：
  - 16-bit → `pcm_s16le`
  - 24-bit → `pcm_s24le`
  - 32-bit → `pcm_f32le`
- **教训**：PCM 系 codec 名字本身就带位深信息，不要再叠加 sample_fmt 参数。

## 2. 误判 ffmpeg.wasm 需要 SharedArrayBuffer

- **现象**：初期以为 0.12 版必须 COOP/COEP 响应头，专门搭了 Node 服务器。
- **根因**：想当然。实际内嵌的 `@ffmpeg/core@0.12.6` 是单线程版——解出 base64 后 grep 整个 core 文件，`SharedArrayBuffer` / `Atomics` / `pthread` 出现次数均为 **0**。
- **解决**：删掉服务器，单 HTML 直接双击运行。
- **教训**：先验证再搭基础设施。判断方法：解出 base64 后 grep 关键字，几分钟的事。

## 3. CDN 版本不存在，下载"伪装"成成功

- **现象**：curl 下载 `@ffmpeg/ffmpeg@0.12.10` 显示成功，文件却只有 52 字节。
- **根因**：该版本不存在，unpkg 返回 HTTP 200 + 错误信息小文件。
- **解决**：下载后必须校验文件大小；版本号以 `registry.npmjs.org` 的 `dist-tags.latest` 为准（@ffmpeg/core 最新确实是 0.12.10，但 @ffmpeg/ffmpeg 不是）。
- **教训**：下载二进制资源，大小校验是底线，"下载成功"≠文件有效。

## 4. UMD 文件名不是 index.js

- **现象**：按官方 README 找 `dist/umd/index.js` 404。
- **根因**：`@ffmpeg/ffmpeg` 的 UMD 入口是 `ffmpeg.js` + `814.ffmpeg.js`（chunk 文件）；只有 `@ffmpeg/util` 才是 `index.js`。
- **解决**：用 `https://unpkg.com/browse/@ffmpeg/ffmpeg@0.12.6/dist/umd/` 看真实文件列表。
- **教训**：包内文件结构以上游实际发布为准，README 可能过时。

## 5. 裸 base64 内嵌，文件 42MB

- **现象**：全部资源 base64 内联后 HTML 42MB。
- **根因**：base64 本身膨胀 33%，31MB wasm 裸编码就是 41MB。
- **解决**：先 gzip 再 base64：42MB → 13MB（-69%）。运行时用浏览器原生 `DecompressionStream('gzip')` 解压，零依赖。
- **教训**：大二进制进 HTML，压缩+base64 是标准动作；能用浏览器原生 API 就不引第三方库。

## 6. atob 解码 13MB 阻塞主线程约 2 秒

- **现象**：点击转换后界面卡死几秒才动。
- **根因**：`atob()` 是同步 API，13.6MB 字符串在主线程解码。
- **解决**：改用 `fetch('data:application/octet-stream;base64,' + s)` 让浏览器 C++ 层解码，异步不卡界面；老浏览器自动回退 atob。
- **教训**：大数据的 base64 解码优先用 fetch data URI，同步大计算是体验杀手。

## 7. file:// 下 Worker 被浏览器拦截

- **现象**：双击打开 HTML，Worker 模式创建失败。
- **根因**：部分浏览器在 `file://` 协议下禁止 `blob:` 源的 Worker。
- **解决**：主线程降级方案——Worker 失败时改用 `<script>` 标签加载 core，同步执行转换。两种模式封装同一接口，用户无感知。
- **教训**：面向"双击打开"的工具必须给降级路径，不能只在自己环境测通过就下结论。

## 8. Worker 失败回退时重复解压 31MB

- **现象**：Worker 创建失败后，主线程模式又把三个资源解压一遍，白白多等 3-4 秒。
- **根因**：`mkURLs()` 没有缓存，调一次解一次。
- **解决**：`_urls` 变量缓存结果，全局只解压一次。
- **教训**：重逻辑要有 memoize 意识，尤其是失败重试路径——最坏情况下用户等了两倍时间。

## 9. 点击转换才开始初始化，用户干等

- **现象**：上传完点「提升音质」，要等 4-5 秒才动。
- **根因**：解压 + wasm 编译全压在点击之后。
- **解决**：页面加载即预热（`preInit()` 后台跑）+ IndexedDB 缓存解压结果，二次打开秒加载。
- **教训**：重活尽量前移到用户不敏感的时段；能缓存的结果别让用户重复等。

## 10. MP3 模式显示不支持的参数

- **现象**：选 MP3 后还能选 192kHz/24-bit，转换结果不符合预期。
- **根因**：libmp3lame 编码配置本项目只支持 44.1kHz + 16-bit，UI 没有过滤。
- **解决**：`getR()` / `getD()` 按输出格式动态过滤，MP3 只留 44.1kHz + 16-bit。
- **教训**：UI 选项要和编码器实际能力对齐，做不到的别显示。

## 11. 过采样检测误报

- **现象**：正常 44.1k 文件被标红「疑似升采样」。
- **根因**：频谱能量阈值 `thr * 0.08` 对低录音电平文件太敏感。
- **解决**：提高检测门槛（`ratio < 0.35` 且 `sr > 48000` 才报），分析失败时给保守默认值而不是报错。
- **教训**：启发式检测要设保守阈值——误报比漏报更伤用户信任。

## 12. ffmpeg-core 许可变化（升级前必读）

- **现象**：无（预防性记录）。
- **根因**：`@ffmpeg/core` 0.12.6 是 **MIT**；从 0.12.8 起改为 **GPL-2.0-or-later**（FFmpeg 上游许可收紧）。
- **解决**：继续用 0.12.6，README/文档保留 MIT 署名即可。若要升级，需补 GPL 声明与源码获取说明。
- **教训**：内嵌第三方二进制，升级前先查 `registry.npmjs.org` 的 license 字段，别默认许可不变。
